## 한국어

> **공식 서버에서 방을 열려면 방장 동의가 필요합니다.** 원본 1.5.1부터 시그널링 서버가 방장의 동의 기록을 요구합니다. 업데이트 후 처음 한 번 `/p2p consent`로 문구를 읽고 직접 동의해 주세요(자동으로 동의하지 않습니다). 가맹점은 공개 방을 열 때만 필요합니다. Java 21.0.13 / 25.0.5 이하처럼 보안 취약점(CVE-2026-91403)이 패치되지 않은 Java에서는 방이 열리지 않을 수 있습니다 — `/p2p java`로 확인하세요.

원본 instant-p2p 모드 **1.5.1**, 가맹점 모드는 **F4.0.2** 기준입니다.

### 추가
- **원본 1.5.1 / 가맹점 F4.0.2 대응**: 방장 연결에 클라이언트 정보(모드·MC·Java 버전, 플러그인 jar 해시)를 싣고, 공개 방일 때 방 정보·밴 목록·접속자 알림·방 기록 신호(30초 하트비트)·서버 알림(서명 채팅 꺼짐, 제목 필터 등)을 처리합니다. 서버가 거부하면(`banned`, `unofficial`, `need-consent-host` 등) 재시도를 멈추고 이유를 관리자에게 알립니다. 서버가 공개 방을 받지 않는 동안(점검 등)에는 10분마다 한 번만 상태를 확인합니다.
- **`/p2p consent`**: 방장 동의 문구를 보고 직접 동의합니다(공식 서버 rev 3, 가맹점 공개 방 rev 1). 가맹점은 동의가 없으면 공개 방을 올리지 않고 초대 코드 방으로만 엽니다.
- **`/p2p java`**: Java 취약점(CVE-2026-91403) 점검. 패치 안 된 Java면 방 열기를 막고, 운영자가 직접 `fix`(문제 인증서를 서버 프로세스 전체의 TLS 신뢰 목록에서 제외)나 `ignore`(이번 실행만 허용)를 고릅니다. 자동으로 바꾸지 않습니다.
- **`/p2p ban-ip <플레이어|IP> [사유]`, `/p2p pardon-ip <#번호|이름|IP>`, `/p2p ban-list`**: 플러그인 자체 IP 밴 목록. Velocity 같은 프록시와 중계 강제 접속자용입니다. 중계 접속자는 서버 쪽 주소가 접속할 때마다 바뀌므로 **계정으로** 막고(원래 IP는 서버도 모르고 어디에도 남지 않습니다), 직결 접속자는 주소로 막습니다. Paper·Spigot·Fabric에서는 직결 밴을 바닐라 `ban-ip`에도 같이 올립니다.
- **다이얼로그**: 가맹점 약관·동의 문구가 채팅에서 잘리던 문제를, MC 1.21.6+ (Paper는 1.21.7+)의 플레이어에게는 스크롤되는 창으로 보여 줍니다. 그 밖의 환경은 지금처럼 채팅으로 나옵니다.
- **가맹점 F4 공개 방**: 공개 방 로비 태그를 가맹점 F4 방식(모드 버전 앞 두 마디)으로 계산해 F4 클라이언트의 방 목록에 보입니다.

### 개선·수정
- **원본 1.5.x부터 중계 접속자의 주소가 접속마다 계속 바뀌는 것을 IP 밴이 유동적으로 따라가도록 바꿨습니다.** 원본 1.5.x 클라이언트는 접속할 때마다 중계(TURN) 할당을 새로 잡기 때문에, 서버가 보는 중계 접속자의 합성 주소가 접속마다 달라집니다(공식·가맹점 서버 모두 확인). 그래서 주소만 막는 `/ban-ip`로는 같은 사람이 다시 들어오는 것을 막지 못했습니다. 이제 중계 접속자는 **계정에 연결해서** 막습니다 — 주소가 바뀌어도 같은 계정은 계속 막히고, 다른 중계 접속자에게는 영향이 없습니다. 원래 IP는 서버도 모르고 어디에도 남지 않습니다. Paper·Spigot·Fabric에서는 바닐라 `/ban-ip`로 막은 중계 접속자도 같은 계정이 새 주소로 들어오면 막습니다. 원본 1.5.1 클라이언트로 LAN을 열었을 때는 중계 접속자의 실제 IP를 알 수 없어 `/ban-ip`가 "실제 IP를 알 수 없습니다"로 거부되고 계정 밴만 되는데(디컴파일된 코드 기준), 서버 통합판은 `/p2p ban-ip`로 중계 접속자도 IP 밴처럼 다룰 수 있습니다.
- 보안·안정성: 사설망·링크 로컬 후보 주소 거부(내부망으로 체크 패킷이 나가는 것 방지), 깨진 패킷이 수신 루프를 죽이지 않게 방어, 모르는 주소에서 UDP가 몰릴 때 걸러내기, 출발지별 연결 상한과 업로드 속도 제한, 협상 자리가 없을 때 즉시 "바쁨" 응답, 재접속 백오프 개선, QUIC 연결 시작 때 주소 검증(Retry).
- **서버를 며칠씩 켜 둘 때를 위한 연결 유지(원본 1.5.1)**: 30초마다 공인 주소를 다시 확인해 바뀌면 새 접속자에게 새 주소를 알리고(공유기 재부팅·회선 교체 대비), 60초마다 중계 경로를 스스로 점검해 연속 3번 실패하면 중계 할당을 새로 잡습니다(서버는 살아 있다고 답하는데 실제로는 못 쓰는 "조용히 죽은 중계" 대비). TURN 권한·채널 개수에도 상한을 뒀습니다.
- Velocity에서 접속자가 나갈 때 `Connection reset` 오류가 찍히던 것을 줄였습니다(터널을 정리해서 닫습니다).
- 모드 클라이언트에 보내는 방 등급 목록을 64명으로 제한했습니다(초과하면 클라이언트가 패킷을 거부합니다).

### 알아 둘 점
- **중계 강제 접속자의 서버 쪽 주소는 접속할 때마다 바뀝니다.** 주소가 고정돼 있어야 하는 기능(주소 기준 연속 접속 제한 등)은 중계 접속자에게 기대하지 마세요. 밴은 `/p2p ban-ip <플레이어>`나 계정 밴을 쓰세요.
- 새로 생기는 파일(데이터 폴더): `consent.json`(방장 동의 기록), `p2p-bans.json`(`/p2p ban-ip` 목록), `relay-links.json`(중계 접속자 계정과 지난 합성 주소 기록 — 실제 IP는 담지 않습니다).
- 원본 클라이언트가 하는 **채팅 자동 검사와 월드 이벤트 기록(블록·표지판·사망 등)은 서버 통합판에서 하지 않습니다.** 방 기록에는 입퇴장과 서버가 살아 있다는 신호만 보냅니다. 원본 1.5의 **유저 신고 기능에서 시그널링 서버가 방장에게 묻는 신고 앞뒤 채팅·표지판·책 내용에도 서버 통합판은 답하지 않습니다**(신고 증거를 보내지 못합니다).
- Velocity는 접속자가 나간 뒤에도 15~30초 동안 세션을 들고 있을 수 있어, 그 사이 같은 계정이 재접속하면 "이미 연결됨"으로 거부될 수 있습니다. `velocity.toml`의 `kick-existing-players = true`로 두면 해결됩니다.
- 시험한 서버: Paper 1.21.11·26.3, Spigot 1.21.11, Fabric 1.21.11·26.3, Velocity 3.5.1·4.2.1 (직결·중계 입장, 밴, 최대 인원, 대량 청크 이동). 공식 서버의 공개 방 목록 노출은 서버 점검 중이라 확인하지 못했고, 가맹점 공개 방은 방 목록 노출과 접속까지 확인했습니다. Fabric의 다이얼로그는 클라이언트 화면까지는 확인하지 못했습니다(실패하면 채팅으로 나옵니다).

**업데이트:** jar만 바꾸고 재시작하면 됩니다. 로그인 정보·초대 코드·설정은 그대로 이어집니다. 공식 서버를 쓰는 경우 `/p2p consent`를 한 번 해 주세요.

## English

> **Opening a room on the official server now requires the host's consent.** Since the original 1.5.1, the signaling server requires a consent record from the host. After updating, run `/p2p consent` once, read the text and agree yourself (it is never accepted automatically). On the franchise server it is only needed for public rooms. On a Java that is not patched for CVE-2026-91403 (e.g. 21.0.13 / 25.0.5 and older) the room may not open — check with `/p2p java`.

Targets the original instant-p2p mod **1.5.1** and the franchise mod **F4.0.2**.

### Added
- **Support for original 1.5.1 / franchise F4.0.2**: the host connection now carries client info (mod / MC / Java version, plugin jar hash), and for public rooms it sends room info, the ban list, join notices, a room-log signal (30-second heartbeat) and handles server notices (signed chat off, title filtered, etc.). When the server refuses (`banned`, `unofficial`, `need-consent-host`, …) it stops retrying and tells the admins why. While the server is not accepting public rooms (maintenance etc.) it only rechecks every 10 minutes.
- **`/p2p consent`**: read the host consent text and agree yourself (official server rev 3, franchise public rooms rev 1). Without it, the franchise server opens the room as an invite-code room only, not public.
- **`/p2p java`**: Java vulnerability (CVE-2026-91403) check. On an unpatched Java it blocks opening rooms; the operator chooses `fix` (removes the affected certificates from the whole server process's TLS trust list) or `ignore` (allow for this run). Nothing is changed automatically.
- **`/p2p ban-ip <player|IP> [reason]`, `/p2p pardon-ip <#id|name|IP>`, `/p2p ban-list`**: the plugin's own IP ban list, for proxies such as Velocity and for relay-forced guests. A relay guest's server-side address changes on every connection, so they are banned **by account** (their real IP is unknown to the server and stored nowhere); direct guests are banned by address. On Paper, Spigot and Fabric, direct bans are also added to the vanilla `ban-ip`.
- **Dialogs**: the franchise terms and consent texts that were cut off in chat are now shown as a scrollable window to players on MC 1.21.6+ (Paper 1.21.7+). Other environments still use chat.
- **Franchise F4 public rooms**: the public room lobby tag is computed the F4 way (first two segments of the mod version), so rooms show up in the F4 client's list.

### Improvements & fixes
- **IP bans now follow the ever-changing address of relay guests (original 1.5.x).** The original 1.5.x client allocates a fresh relay (TURN) allocation on every connection, so the synthetic address the server sees for a relay guest differs on each join (confirmed on both the official and the franchise server). Banning by address alone therefore could not stop the same person from coming back. Relay guests are now banned **by account**: the same account stays blocked whatever address it gets, and other relay guests are not affected. The real IP is unknown to the server and stored nowhere. On Paper, Spigot and Fabric, a relay guest banned with vanilla `/ban-ip` is also blocked when the same account returns with a new address. With the original 1.5.1 client hosting a LAN, the real IP of a relay guest is unknown, so `/ban-ip` is refused ("cannot resolve the real IP") and only an account ban works (per the decompiled code); the server edition lets `/p2p ban-ip` handle relay guests like an IP ban.
- Security and stability: rejects private-network / link-local candidate addresses (so check packets cannot be sent into an internal network), malformed packets can no longer kill the receive loop, filters UDP floods from unknown addresses, per-source connection limits and upload rate limit, instant "busy" reply when no negotiation slot is free, better reconnect backoff.
- **Long-uptime resilience (original 1.5.1)**: re-checks the public address every 30 s and, if it changed, announces the new one to new guests (router reboot, line change); checks the relay path every 60 s and, after 3 consecutive failures, allocates a fresh relay (a "silently dead relay" the server still reports as alive). TURN permissions and channels are capped. QUIC connections now start with address validation (Retry).
- Fewer `Connection reset` errors logged by Velocity when a guest leaves (the tunnel is now closed gracefully).
- The room rank list sent to the mod client is capped at 64 entries (the client rejects larger packets).

### Notes
- **The server-side address of a relay-forced guest changes on every connection.** Do not rely on features that need a stable address (per-address connection throttling, etc.) for relay guests. Use `/p2p ban-ip <player>` or an account ban to ban them.
- New files (data folder): `consent.json` (host consent record), `p2p-bans.json` (the `/p2p ban-ip` list), `relay-links.json` (relay guest account ↔ past synthetic addresses; no real IPs).
- The original client's **automatic chat scanning and world-event logging (blocks, signs, deaths, …) are not done by the server edition.** The room log only carries joins/leaves and a "server is alive" signal. The server edition also **does not answer the signaling server's report-evidence queries** (chat / sign / book context around a user report, original 1.5) — it cannot send report evidence.
- Velocity may keep a session for 15–30 seconds after a guest leaves, so the same account reconnecting in that window can be refused with "already connected". Set `kick-existing-players = true` in `velocity.toml` to fix this.
- Tested on: Paper 1.21.11 / 26.3, Spigot 1.21.11, Fabric 1.21.11 / 26.3, Velocity 3.5.1 / 4.2.1 (direct and relay joins, bans, player limit, heavy chunk loading). Public room listing on the official server could not be checked (server under maintenance); franchise public rooms were verified through the room list and joining. The Fabric dialog was not verified on a client screen (it falls back to chat).

**Updating:** replace the jar and restart. Login data, invite code and settings carry over. If you use the official server, run `/p2p consent` once.
